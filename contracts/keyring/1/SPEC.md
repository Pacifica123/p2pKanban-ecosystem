# `p2p-kanban-keyring/1` — связка ключей аккаунта

Статус: описан в R1 (2026-10-06), ни одно направление его ещё не реализовало.
Требует [`account-ring/1`](../../account-ring/1/SPEC.md). Порядок реализации:
web (R2) → mobile (R3) → abl (R6).

Связка заменяет каталог «на каждую доску отдельно». Одна связка на аккаунт:
все пространства, включая пустые, и все доски с ключами `roaming/1`. Доска,
созданная в поездке, появляется на остальных устройствах со следующей связкой,
без повторной привязки.

Связка делает доски видимыми и открываемыми. Структуру доски (колонки,
переименования) она не переносит: это отдельная работа, уже записанная долгом
в web и mobile.

## Содержимое

```json
{
  "protocol": "p2p-kanban-keyring/1",
  "accountId": "<id genesis кольца>",
  "ringHeads": ["<головы журнала кольца, которые видел автор>"],
  "items": [ {"kind": "space", ...}, {"kind": "board", ...} ]
}
```

Схемы: [keyring.schema.json](schema/keyring.schema.json),
[item.schema.json](schema/item.schema.json).

Общие поля элемента: `kind`, `id` (UUID), `rev` (целое ≥ 1, растёт при каждом
изменении элемента), `updatedBy` (ключ устройства), `deleted`.

| `kind` | Поля | Смысл |
|---|---|---|
| `space` | `name` | пространство (workspace); пустое тоже распространяется |
| `board` | `spaceId`, `name`, `roaming: {protocol: "p2p-kanban-roaming/1", epoch, boardKey}` | доска и её ключ текущей эпохи доступа |

`boardKey` — 32 байта base64url, тот самый ключ `roaming/1`. Тег доски
выводится из него по `roaming/1` и в связке не хранится. В кольце писателями
доски `roaming/1` считаются текущие участники кольца, поэтому отдельный список
writer-ключей связка не несёт. Web-узел может и дальше выводить `boardKey` из
своего `masterKey`: для остальных ключ непрозрачен.

У удалённого элемента `deleted: true` и нет поля `roaming`.

## Кто публикует

Любой участник кольца (admin и member): создал пространство или доску —
публикует новую связку. Связка ходит в запечатанной записи `kind 31991` под
тегом аккаунта, для всех текущих участников
([конверт](../../account-ring/1/SPEC.md#публикация-на-relay-запечатанная-запись)),
и внутри `welcome` при встрече. Копии от устройства, которое не участник по
журналу кольца, читатель не принимает.

## Слияние

Каждое устройство публикует свою копию; читатель сливает все копии
(`merge_keyrings` в эталоне), и результат не зависит от их порядка:

1. элементы группируются по паре (`kind`, `id`);
2. в группе побеждает наибольший ключ (`roaming.epoch` или 0, `rev`,
   sha256 канонической формы элемента в hex): ротированный ключ новой эпохи
   побеждает любой `rev` старой эпохи, а равенство решает хеш, а не время;
3. удаление необратимо: если хоть одна копия удалила элемент, итог —
   победитель без `roaming` с `deleted: true`;
4. элемент неизвестного `kind` и неизвестные поля переносятся как есть.
   Устройство старой версии, переопубликовав связку, не стирает то, что
   записала новая.

`digest` связки (для отметки присутствия и сравнения устройств) — sha256
канонической формы списка победителей, отсортированного по (`kind`, `id`).

Вектор: [merge.json](vectors/merge.json). В нём пустое пространство из поездки
доходит до узла, ротированный ключ эпохи 2 побеждает больший `rev` эпохи 1,
удаление доски убирает её ключ, а элемент вида `calendar` от новой версии
сохраняется. Запечатанная копия: [sealed-keyring.json](vectors/sealed-keyring.json).

## Ротация после удаления устройства

После `remove` в журнале кольца (R5) admin выпускает для каждой доски новый
`boardKey` с `epoch + 1` и публикует связку только для оставшихся участников.
Удалённое устройство сохранит то, что уже получило, но новых данных не
прочитает. До R5 удаление закрывает доступ к журналу кольца и новым связкам,
но не к доскам со старым ключом: это видно на экране кольца как «ключи не
ротированы после удаления».

## Свежесть

Поручитель во встрече (rendezvous/1) обязан отдать связку, согласованную с
журналом: её `ringHeads` равны текущим головам кольца. Если связка отстаёт,
поручитель сначала синхронизируется, а если не может — отказывает с причиной
`sponsor-stale`.
