# Общие контракты экосистемы

Здесь лежат контракты, которые производят и потребляют несколько направлений.
У каждого контракта одно место: спецификация, JSON Schema и эталонные векторы
рядом, с версией в пути.

```text
contracts/
  compatibility.json          кто какой контракт реализует, с какой версии, порядок обновления
  common/defs.schema.json     общие определения схем
  <контракт>/<версия>/
    SPEC.md                   правила, которые нельзя выразить схемой
    schema/*.schema.json      форма данных на проводе (JSON Schema 2020-12)
    vectors/*.json            эталонные примеры с ожидаемым результатом
```

| Контракт | Каталог | Что описывает | Статус |
|---|---|---|---|
| `p2p-kanban-account-ring/1` | [account-ring/1](account-ring/1/SPEC.md) | журнал кольца устройств аккаунта, запечатанные записи на relay, отметки присутствия | описан (R1), не реализован |
| `p2p-kanban-keyring/1` | [keyring/1](keyring/1/SPEC.md) | связка ключей аккаунта: пространства и доски с ключами | описан (R1), не реализован |
| `p2p-kanban-rendezvous/1` | [rendezvous/1](rendezvous/1/SPEC.md) | добавление устройства по QR в двух режимах через почтовый ящик на relay | описан (R1), не реализован |
| `p2p-kanban-error-report/1` | [error-report/1](error-report/1/SPEC.md) | «Скопировать подробности» у любой ошибки в web, mobile и abl: форма отчёта, вырезание секретов, id ошибки и версия в ответах web-узла | описан, не реализован |

Зачем кольцо, рассказывает [docs/ecosystem/trusted-devices.md](../docs/ecosystem/trusted-devices.md);
зачем отчёт об ошибке — его [SPEC](error-report/1/SPEC.md) и карточка «Сборщик логов» на доске.
Прежние контракты (`roaming/1`, `sync/1`, `device-link/2`, `web-node-link/1`,
`p2p_planner_bundle` v1) пока описаны внутри направлений; их перенос сюда —
карточка «Вынести контракты в contracts/».

## Проверка

```bash
python -B tools/ecosystem/check_contracts.py
```

Только стандартная библиотека Python. Проверка сверяет эталонную криптографию с
опубликованными векторами BIP-340 и NIP-44, прогоняет каждый вектор через схемы
и через эталонную реализацию `tools/ecosystem/contract_ref.py` и требует, чтобы
файлы векторов совпадали с генератором `tools/ecosystem/contract_vectors.py`
байт в байт. Вектор нельзя поправить руками: правится генератор, затем

```bash
python -B tools/ecosystem/contract_ref.py generate
```

Эталонная реализация медленная и не защищена от атак по времени. Она отвечает
на вопрос «как правильно», а продуктовый код направления пишет своими
библиотеками.

## Как направление пользуется контрактом

Направление остаётся суверенным: оно не импортирует код из корня. Его тесты
читают `contracts/<контракт>/<версия>/vectors/*.json` (из корня репозитория
или из копии, которую направление делает при сборке; выбирает само
направление) и требуют того же результата: тех же id событий, того же
состояния кольца, тех же расшифровок. Если формат меняется, вектор меняется
в том же патче, и тест потребителя падает сразу, а не на телефоне в поездке.

Когда направление реализует контракт, тот же патч заполняет
`implementations.<направление>` в [compatibility.json](compatibility.json):
`since` (версия направления), `stage` (этап R2–R6), `hostAccepted` (принято ли
на хосте). Приёмка на хосте отдельным патчем ставит `hostAccepted: true`.

## Общие примитивы

Новых криптографических семейств нет: всё уже стоит в каждом направлении.

| Что | Как | Где уже есть |
|---|---|---|
| ключ устройства | secp256k1, x-only публичный ключ 32 байта, hex | web `nostr-sdk`, mobile `nostr-tools`, abl `k256` |
| подпись | событие Nostr (NIP-01), подпись BIP-340 Schnorr | `roaming/1`, `device-link/2` |
| шифрование для одного получателя | NIP-44 v2 | `device-link/2` (передача снимка) |
| симметричное шифрование | XChaCha20-Poly1305, nonce 24 байта | `roaming/1` |
| вывод ключей | HMAC-SHA256, HKDF-SHA256 | `roaming/1`, NIP-44 |
| двоичное в JSON | base64url без `=`; NIP-44 payload — обычный base64, как в NIP-44 | |
| каноническая форма JSON | ключи по алфавиту, без пробелов, UTF-8 без `\u`-экранирования не-ASCII | содержимое событий кольца |

Подпись и id события считаются по строке `content` как она есть. Читатель
никогда не пересериализует `content` перед проверкой: поэтому неизвестные поля
от новой версии не ломают подпись у старой.

|---|---|---|---|
| 1979 | событие доски | да | `roaming/1` (не меняется) |
| 27780–27782 | цепочки и передача `device-link/2` | эфемерные | `device-link/2` (не меняется) |

| 1991 | сообщение почтового ящика встречи | да, с тегом `expiration` (NIP-40) | `rendezvous/1` |

## Разные версии на устройствах

Приёмка mobile на хосте часто отстаёт: на телефоне может стоять старый APK,
пока web и abl уже новые. Поэтому контракты кольца устроены так, чтобы
отставание было видно, а не молча считалось нормой.

1. **Каждое сообщение называет свой протокол** (`protocol` или `v`). Читатель,
   встретив больший номер того же контракта, не угадывает, а говорит:
   «это от более новой версии, обновите это устройство».
2. **Неизвестные поля игнорируются, но не отбрасываются.** Устройство, которое
   переопубликует связку или журнал, переносит чужие поля и элементы как есть.
   Старый телефон не стирает то, что записал новый узел.
3. **Неизвестный тип записи журнала хранится, но не применяется**, а
   устройство считает себя устаревшим (`readerOutdated`): показывает это на
   экране кольца и не пишет записи, меняющие состав (`add`, `remove`,
   `relays`), пока не обновится. Доски при этом синхронизируются как раньше.
4. **Отметка присутствия несёт версию программы и список протоколов.** Экран
   кольца на любом устройстве показывает строку вида «Телефон: mobile 2.2.0,
   не знает keyring/1, видел журнал до последнего изменения». Вектор
   [presence.json](account-ring/1/vectors/presence.json) фиксирует, как это
   считается.
5. **Встреча проверяет версии до добавления.** Если входящее устройство не
   знает нужных протоколов, поручитель отказывает с причиной
   `joiner-outdated` и показывает, что обновить.
6. **Старые клиенты без кольца продолжают работать.** `roaming/1` не меняется,
   `device-link/2` читается до R5. Устройство без кольца видно на экране кольца
   отдельной строкой «вне кольца, старая версия», со сроком его доступа.
   Правила — в разделе `legacy` [compatibility.json](compatibility.json).

## Как меняется контракт

- Добавить необязательное поле, новый тип записи или вид элемента можно в той
  же версии: старые читатели его сохранят и сообщат, что устарели.
- Всё остальное — новая версия в новом каталоге (`account-ring/2/`), а старая
  остаётся, пока в `compatibility.json` есть направление, которое её читает.
- Патч, меняющий контракт, называет его в `summary`, обновляет векторы и
  указывает порядок обновления: **web-узлы → mobile → abl**.
