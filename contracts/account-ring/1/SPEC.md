# `p2p-kanban-account-ring/1` — журнал кольца устройств аккаунта

Статус: описан в R1 (2026-10-06), ни одно направление его ещё не реализовало.
Порядок реализации: web (R2) → mobile (R3) → abl (R6).

Аккаунт — это кольцо устройств. Каждое устройство держит свой ключ и полную
копию журнала кольца. Кто входит в кольцо, решает журнал, а не цепочка со
сроком: членство бессрочно, пока его явно не отменят записью `remove`.
Зачем так, рассказывает [trusted-devices.md](../../../docs/ecosystem/trusted-devices.md).

## Ключ устройства

Ключ устройства — secp256k1, тот же, которым устройство подписывает события
`roaming/1`. Нового ключа не появляется. Публичный ключ записывается как 64
символа нижнего hex (x-only, как `pubkey` в Nostr). Секрет не покидает
устройство: web держит его в настройках узла, mobile в SecureStore, abl в
`SecretVault`.

Удалённый ключ нельзя вернуть в кольцо. Устройство, которое удалили по ошибке,
возвращается с новым ключом.

## Запись журнала

Запись — событие Nostr (NIP-01) `kind 27790` без тегов, подписанное ключом
устройства, которое её делает. `content` — JSON-объект строкой:

| Поле | Обязательно | Смысл |
|---|---|---|
| `protocol` | да | `"p2p-kanban-account-ring/1"` |
| `type` | да | `genesis`, `add`, `remove`, `rename`, `relays` или тип от более новой версии |
| `accountId` | кроме `genesis` | id записи `genesis` этого кольца |
| `parents` | да | id записей, которые были головами журнала у автора; у `genesis` пустой список, у остальных 1–16 |

Журнал — направленный граф без циклов: каждая запись ссылается на головы,
которые видел её автор. Записи, сделанные на разных устройствах одновременно,
дают ветви; следующая запись любого устройства, видевшего обе ветви, их
сливает. Хеш-ссылки делают цикл невозможным.

| `type` | Поля | Кто вправе | Что меняет |
|---|---|---|---|
| `genesis` | `nonce` (≥ 16 случайных байт, base64url), `device`, `relays` | подписант = `device.publicKey`, роль `admin` | создаёт кольцо; `accountId` := id этой записи |
| `add` | `device`, `via`: `rendezvous` или `migration` | admin | новое устройство в кольце |
| `remove` | `publicKey`, `reason`: `lost`, `replaced`, `left`, `other` (необязательно) | admin; любой участник — сам себя | устройство исключено навсегда |
| `rename` | `publicKey`, `name` | admin; любой участник — сам себя | новое имя устройства |
| `relays` | `relays` | admin | новый набор relay кольца |

`device` = `{publicKey, name (1–64 символа), kind: web | android | arch, role: admin | member}`.
`relays` = `{urls: 1–16 адресов wss://, minAcks: 1..len(urls)}`; по умолчанию три
relay и два подтверждения. `via: migration` пишет только web при переносе
доверия из `device-link/2` и `web-node-link/1` (R2).

Схемы: [entry.schema.json](schema/entry.schema.json),
[entry-content.schema.json](schema/entry-content.schema.json).

## Свёртка журнала в состояние

Все устройства обязаны получать одно и то же состояние из одного и того же
множества записей, в каком бы порядке записи ни пришли. Эталон —
`fold_ring` в [tools/ecosystem/contract_ref.py](../../../tools/ecosystem/contract_ref.py).

1. **Разбор.** Отбросить запись с неверным id или подписью, чужим kind,
   `content` длиннее 16 КиБ или не-JSON, другим `protocol`, неверными
   `parents`. Запись с `protocol` вида `p2p-kanban-account-ring/N`, N > 1,
   помечает читателя устаревшим. Одинаковые id считаются одной записью.
2. **Аккаунт.** `genesis` — запись, id которой равен ожидаемому `accountId`.
   Записи с другим `accountId` и прочие `genesis` отклоняются.
3. **Ожидание.** Запись, у которой неизвестен хотя бы один предок, ждёт
   (`pending`) вместе со всеми потомками. Устройство запрашивает недостающее
   у relay и у других устройств; ожидающие записи не влияют на состояние.
4. **Порядок.** Топологическая сортировка; среди записей, готовых
   одновременно, раньше идёт меньший id (строкой hex). Этот порядок нужен
   только для `rename` и `relays`: побеждает последняя допустимая.
5. **Фаза A — права в прошлом.** Для каждой записи по порядку построить
   состояние из допустимых записей её причинного прошлого (всех предков) и
   проверить права по таблице выше. Дополнительно:
   `add` уже удалённого ключа — `key-was-removed`; `add` участника —
   `already-member`; `remove` неизвестного — `unknown-target`; `remove`
   последнего admin в этом прошлом — `last-admin`; запись от неучастника —
   `signer-not-member` или `signer-removed`.
6. **Фаза B — заморозка.** Пусть устройство S удалено допустимыми в фазе A
   записями `remove`. Любая другая запись S (не `remove`), которой нет в
   прошлом ни одной из этих `remove`, отклоняется как `frozen-by-remove`.
   Смысл: удаляющий утверждает то, что S сделал на его глазах, и только это.
   Украденное устройство не может задним числом добавить чужое устройство,
   выбрав старых предков.
7. **Фаза C — каскад.** Повторить фазу A, исключив замороженные записи. Всё,
   что держалось на них (например, записи устройства, добавленного украденным
   телефоном), отклоняется. Записи `remove`, допустимые в фазе A, действуют
   всегда: удаление консервативно.
8. **Состояние.** Применить допустимые записи по порядку: участники с именем,
   типом, ролью, кем и какой записью добавлены; удалённые ключи с записью
   удаления; набор relay; головы (записи без потомков среди разобранных).

Следствия, которые зафиксированы векторами:

| Сцена | Итог | Вектор |
|---|---|---|
| обычная жизнь кольца | узел, телефон, ноутбук; имя и relay сменены | [ring-linear](vectors/ring-linear.json) |
| параллельные `add` с разных устройств | оба устройства в кольце | [ring-concurrent-add](vectors/ring-concurrent-add.json) |
| телефон украден; узел удаляет его, не видя, что телефон добавил чужое устройство | чужое устройство не в кольце, его записи отклонены каскадом | [ring-stolen-phone](vectors/ring-stolen-phone.json) |
| телефон добавил ноутбук, узел видел это и потом удалил телефон | ноутбук остаётся | [ring-remove-after-seen-add](vectors/ring-remove-after-seen-add.json) |
| два устройства одновременно удаляют друг друга | выходят оба; кольцо продолжают остальные | [ring-mutual-remove](vectors/ring-mutual-remove.json) |
| запись неизвестного типа от новой версии | хранится, не применяется, читатель устарел | [ring-newer-writer](vectors/ring-newer-writer.json) |
| нарушения прав, подделка, сирота, чужой аккаунт, протокол /2 | у каждого своя причина | [ring-rejections](vectors/ring-rejections.json) |

Причины отказа (`rejected[].reason`): `bad-id`, `bad-signature`,
`malformed-event`, `wrong-kind`, `too-large`, `malformed-content`,
`foreign-protocol`, `bad-parents`, `foreign-account`, `duplicate-genesis`,
`signer-not-member`, `signer-removed`, `signer-not-admin`, `key-was-removed`,
`already-member`, `unknown-target`, `last-admin`, `frozen-by-remove`.
Направление может называть их по-своему в интерфейсе, но в журнале и логах
пишет эти коды.

## Новая запись

`parents` — текущие головы журнала у автора, `created_at` — текущее время
(только для людей: порядок от него не зависит). Голов больше 16 при десятках
устройств не бывает; если всё же так, запись берёт 16 наименьших по id, а
следующая — остальные. Права проверяются по собственному текущему состоянию
до отправки. Устройство с `readerOutdated` не пишет `add`, `remove` и
`relays`.

## Публикация на relay: запечатанная запись

Записи журнала никогда не публикуются открыто. Каждое устройство публикует
свою копию журнала целиком, зашифрованную для всех текущих участников:

- событие `kind 31990` (заменяемое: relay хранит последнее по паре
  «устройство, тег»), подписанное ключом устройства;
- теги `["d", accountTag]`, `["t", "p2pkanban-ring"]`, `["v", "1"]`;
- `accountTag = base64url(HMAC-SHA256(key = bytes(accountId), "p2p-kanban:account-tag:v1"))`;
- `content` — JSON [sealed-record](schema/sealed-record.schema.json):

```json
{"version": 1, "type": "ring-log", "nonce": "<24 байта>", "ciphertext": "<…>", "recipients": ["<NIP-44>", "…"]}
```

Как запечатать: взять случайный ключ содержимого `cek` (32 байта) и nonce (24
байта); `ciphertext = XChaCha20-Poly1305(cek, nonce, plaintext, aad)`, где
`aad = "p2p-kanban:seal:v1|<type>|<accountTag>"`, а `plaintext` — открытое
содержимое в канонической форме JSON; для каждого участника
`NIP-44 v2(секрет отправителя, ключ участника, base64url(cek))`; список
`recipients` отсортировать, чтобы порядок не выдавал состав. Получатель
перебирает `recipients` своим conversation key (ошибка MAC — не его слот).

Открытое содержимое `ring-log`: `{protocol, accountId, entries: [события kind 27790]}`
([ring-log.schema.json](schema/ring-log.schema.json)). Читатель сливает все
копии под тегом аккаунта как множество записей и сворачивает заново. Копия
от устройства, которое не участник в итоговом состоянии, всё равно может
принести записи: подпись проверяется у каждой записи, а не у копии.

Тот же конверт с `type: keyring` (`kind 31991`) несёт связку ключей
([keyring/1](../../keyring/1/SPEC.md)), с `type: presence` (`kind 31992`) —
отметку присутствия. Вектор: [sealed-ring-log.json](vectors/sealed-ring-log.json).

## Отметка присутствия

Пока приложение открыто, устройство раз в несколько минут (интервал решает
направление) публикует `kind 31992` для всех участников:

| Поле | Смысл |
|---|---|
| `publicKey` | само устройство; равно `pubkey` события |
| `seenAt` | когда опубликовано |
| `software` | `{direction: web, mobile или abl, version, protocols: [...]}` |
| `ringHeads` | головы журнала, которые устройство видит |
| `keyring` | `{digest, items, boards}` связки или `null`, если устройство её не знает |
| `relays` | `[{url, reachable}]`: какие relay кольца доступны устройству |
| `boards` | необязательно: `[{boardId, keyEpoch, baseline}]`, есть ли базовый снимок доски |

Схема: [presence.schema.json](schema/presence.schema.json). Из отметок любое
устройство строит экран «Кольцо устройств» и «Проверку перед поездкой»:
когда виделся каждый участник, через какие relay, совпадает ли связка, кто
отстаёт по версии. Отставание считается так (`presence_skew` в эталоне):
протоколы кольца, которых нет в `software.protocols`, и `ringHeads`,
отличные от текущих голов. Вектор: [presence.json](vectors/presence.json).

## Чего `/1` не делает

- **Тег аккаунта не ротируется.** Удалённое устройство может видеть, что
  кольцо живо (время и размер записей), но не прочитает новое содержимое:
  оно больше не получатель.
- **Слияния двух колец нет.** Встреча с устройством из другого кольца с
  другими участниками останавливается ([rendezvous/1](../../rendezvous/1/SPEC.md)).
- **Кольцо без admin не добавляет устройств.** Правило `last-admin` не даёт
  прийти к этому одной записью, но взаимное удаление может; тогда остальные
  участники продолжают работать, а новое устройство добавляется в новое
  кольцо.
- **Удаление не стирает данные** с выключенного устройства и само не
  ротирует ключи досок: ротация — новая версия связки после `remove` (R5).
