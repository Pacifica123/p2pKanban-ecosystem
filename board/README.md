# Самоприменимая доска экосистемы

`board.json` — доска, на которой экосистема ведёт собственную работу. Это
обычный переносимый файл доски p2pKanban (`p2p_planner_bundle` v1,
`portable_export`, одна доска), поэтому его открывает сам продукт.

## Как открыть доску в продукте

Доска встроена в каждый клиент только для чтения: пункт «Доска проекта»
показывает старшую из известных клиенту ревизий (копия в сборке, кеш, узел,
`main` на GitHub у web-узла) и подписывает, откуда она. В синхронизацию она
не входит, поэтому подключение узлов её не размножает. Правила —
[`contracts/project-board/1/`](../contracts/project-board/1/SPEC.md), решение —
[E-ADR-003](../docs/ecosystem/adr/E-ADR-003-project-board-in-clients.md). Кто
уже показывает доску, записано в `contracts/compatibility.json`.

Черновик для правок по-прежнему делается импортом копии:

| Направление | Как | Что важно |
|---|---|---|
| web | список досок нужного workspace → «Импорт доски из JSON» → «Создать копию» | web создаёт копию с новыми ID; комментарии получат текущего автора |
| abl | импорт переносимой доски (A11) | только в пустой профиль; исходные ID сохраняются |
| mobile | пока нельзя: импорт ещё не перенесён из web | карточка «Импорт доски в Android» |

Источник истины — файл в репозитории. Копия в продукте — способ посмотреть и
подумать; изменения возвращаются в репозиторий патчем. Копии файла в
сборках направлений обновляет `python -B tools/ecosystem/project_board.py
vendor <направление>`.

## Номер патча в версии клиентов

web, mobile и abl показывают рядом со своей версией, из какого патча собраны:
«патч 34 · 2026-10-17-web-build-patch». Номер — `origin.boardRevision`, имя —
`origin.lastPatchId`. Оба поля обновляет каждый патч, поэтому пара называет
последний патч, применённый к дереву, из которого шла сборка, и номера идут
подряд.

Сборка находит пару так, по порядку:

1. переменные `P2PKANBAN_PATCH_ID` и `P2PKANBAN_PATCH_REVISION`, если заданы
   (сборка вне монорепозитория);
2. файл `BUILD_PATCH.json` (`{"patchId": …, "boardRevision": …}`) в корне
   направления: его пишет тот, кто берёт направление без корня, например
   updater web из архива коммита;
3. `board/board.json` в каталоге выше направления, где лежит и
   `ecosystem.json`. Это чтение корня, а не соседнего направления.
   Направление вправе смотреть только на непосредственного родителя: web так
   и делает, потому что его релизные копии лежат внутри checkout;
4. иначе «патч неизвестен».

`patchId` принимается только из `[0-9A-Za-z][0-9A-Za-z._-]*` (до 128 знаков),
номер — целое от 1. Пара вшивается в клиент при сборке, а не читается при
запуске: старый APK продолжает называть свой патч.

Чего номер не говорит. Ручная правка или коммит без патча после последнего
патча номер не меняют: точное дерево называет коммит, который клиенты уже
показывают (`contracts/error-report/1`). В «Скопировать подробности» номера
пока нет: это изменило бы поле `software` контракта error-report/1.

## Колонки-статусы

| Колонка | Когда карточка здесь |
|---|---|
| Идеи | сырая мысль или наблюдение; не обязательство |
| Обдумать | нужна стратегия, ADR или решение владельца до кода |
| Запланировано | этап из плана направления: объём и порядок известны, начнётся после предшественника, названного в описании |
| Готово к патчу | понятны направление, объём, проверка и критерий готовности |
| В работе | делается текущей серией патчей; не больше двух карточек |
| Ждёт хоста | код и детерминированные проверки есть, нужна приёмка на телефоне, Arch или Docker |
| Сделано | принято; в комментарии есть `patchId` |
| Отложено | сознательно не сейчас; в описании сказано почему |

Карточка движется слева направо, но может вернуться: из «Ждёт хоста» в
«В работе», если хост нашёл ошибку. Из «Сделано» карточки не возвращаются:
новая проблема — новая карточка.

Колонка «Запланировано» появилась, когда на доску переносили дорожные карты
направлений: этап, который ждёт предыдущий этап, ещё не «Готов к патчу», но
уже и не нуждается в решении.

## Дорожные карты направлений

Планы, записанные внутри направлений, перенесены на доску. Источник истины о
содержании этапа — документ направления; доска отражает статус.

| Направление | Источник плана | Где на доске |
|---|---|---|
| abl | `abl/docs/IMPLEMENTATION_STATUS.md`, `abl/docs/NEXT_PATCH_SEQUENCE.md`, `abl/docs/architecture/07-roadmap-devctl-tests-experiments-do-not.md` | A15–A17 в «Ждёт хоста», A18 и Gate G в «Запланировано», A19 в «Идеи», DEBT-A00-001 в «Обдумать» |
| web | `web/docs/product/v1-execution-roadmap.md`, `web/docs/product/v1-remaining-checklist.md`, `web/docs/architecture/shared-history-and-node-connectivity.md` | полевое подтверждение v1 в «Ждёт хоста», GitHub и Obsidian в «Обдумать» и «Запланировано», будущие срезы в «Идеи» |
| mobile | `mobile/docs/architecture/replica-recovery-20260915.md` (долги) | компакция журнала в «Обдумать», межсетевая приёмка в «Ждёт хоста» |
| экосистема | `docs/ecosystem/trusted-devices.md` | эпик кольца устройств в «Обдумать», этапы R0–R6 по колонкам |

## Метки

У каждой карточки есть хотя бы одна метка направления: `web`, `mobile`, `abl`,
`devctl`, `launcher` или `экосистема`. Дополнительно: `контракт` (меняет связь между
направлениями), `риск`, `долг`.

## Описание карточки

```text
Зачем: какую проблему это решает.

Готово, когда: проверяемый результат.

(необязательно) Ограничения, принципы, почему не сейчас.
```

## Обновление в каждом патче

Обязательно (проверяется `tools/ecosystem/check_board.py --require-changed`):

- `origin.boardRevision` увеличен на 1;
- `origin.lastPatchId` — идентификатор этого патча, `origin.generatedAt` — его время;
- файл остаётся корректным переносимым bundle для web и abl.

По смыслу (проверяется ревью): карточка патча сдвинута или создана, к ней
добавлен комментарий `patch <patchId>: что стало истинным`, сделанные пункты
чек-листа отмечены. Счётчики в `manifest.json.summary.entityCounts` должны
совпадать с содержимым.

Новые ID — UUID (предпочтительно v7, как в продукте). ID существующих
сущностей не меняются: по ним доска связывается с историей патчей.
