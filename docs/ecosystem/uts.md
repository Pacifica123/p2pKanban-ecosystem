# UTS экосистемы: общий тестер приёмки на хосте

## Решение

Одна команда на машине владельца проверяет все направления сразу и отвечает
на три вопроса:

1. **Принято ли каждое направление?** Бинарно: PASS или FAIL.
2. **Насколько готова экосистема в целом?** В процентах, с разбивкой по
   уровням доказательства, а не одним битом.
3. **Что на самом деле стоит на хосте и телефоне?** Версии развёрнутых узла,
   APK, пакета abl и devctl сверяются с проверяемым деревом. Смесь версий
   выносится в начало отчёта.

```bash
python3 -B tools/ecosystem/uts.py
```

Запускать из корня монорепозитория или из его копии в `UserTestSpace`
(`…/project_<время>_after_<патч>_<sha>/project`). Только стандартная
библиотека Python; инструменты направлений (Docker, npm, cargo, adb, pacman)
нужны только для их собственных проверок. Чего нет — проверка получает
BLOCKED с причиной, прогон продолжается.

Собственный UTS abl (`abl/tools/uts_verify.py`) остаётся каноном abl и
вызывается как одна из проверок: тестер экосистемы не заменяет проверки
направлений, а собирает их в один прогон и один отчёт.

## Флаги

| Флаг | Что делает |
|---|---|
| `--only web,mobile` | только эти направления (`ecosystem`, `web`, `mobile`, `abl`, `devctl`) |
| `--skip build` | пропустить уровни: `static`, `build`, `host`, `device`, `manual` |
| `--allow-network` | `npm ci` может докачать пакеты; UTS abl получает `--allow-network` |
| `--no-runtime` | UTS abl без запуска окна (нет графической сессии) |
| `--interactive` | спросить о каждой карточке колонки «Ждёт хоста» |
| `--web-url URL` | адрес узла, если он не в Docker этого хоста |
| `--out DIR` | куда класть прогоны (по умолчанию `.uts/` в корне дерева) |
| `--list` | показать план и выйти |
| `--self-test` | проверить сам тестер на синтетическом дереве |

По умолчанию сеть не нужна (как и у UTS abl): `npm ci --offline` берёт пакеты
из кэша npm. Первый прогон на новой машине — с `--allow-network`.

Код возврата: `0` — все запущенные направления PASS, `1` — есть FAIL,
`2` — ошибка плана или флагов.

## Уровни, вердикт, готовность

Каждая проверка относится к уровню доказательства:

| Уровень | Вес | Что доказывает |
|---|---|---|
| `static` — исходники | 1 | контракты и тесты, которым хватает Python/Node |
| `build` — сборка | 2 | дерево собирается и проходит тесты своим тулчейном |
| `host` — хост | 3 | развёрнутое на этой машине работает и совпадает с деревом |
| `device` — устройство | 3 | на телефоне стоит сборка из этого дерева |
| `manual` — вручную | 2 | человек подтвердил карточку «Ждёт хоста» |

Статусы: `PASS`, `WARN` (прошло с оговоркой), `FAIL`, `BLOCKED` (не на чем
проверить: нет инструмента, устройства или упала зависимость), `SKIP`
(пропущено флагом или не подтверждено), `INFO` (справка, в счёт не идёт).

- **Вердикт направления** — PASS, только если каждая гейт-проверка дала PASS
  или WARN. BLOCKED и SKIP гейта — это FAIL: непроверенное не принято
  (правило 5 инструкций проекта).
- **Готовность направления** — доля доказанного:
  `Σ вес·зачёт / Σ вес`, где зачёт PASS = 1, WARN = ½, остальное 0, а вес
  не-гейт проверки вдвое меньше веса её уровня.
- **Покрытие** — доля проверок, которые удалось выполнить (не BLOCKED и не
  SKIP). Низкое покрытие при высокой готовности значит «мало что смогли
  проверить».
- **Общая готовность** — среднее готовностей запущенных направлений:
  100 — принято полностью, 90–99 — с оговорками, 70–89 — почти, 40–69 —
  частично, ниже — далеко. Прогон с `--only`, `--skip` или прерванный
  помечается как неполный: это диагностика, не приёмка.

## Расхождение версий

Данность проекта: приёмка mobile на хосте часто отстаёт, и старый APK может
встретиться с новым web. Тестер не доверяет этому молча, а сверяет:

| Направление | Исходники | Развёрнутое | Как сверяется |
|---|---|---|---|
| web | `web/VERSION`, коммит дерева, отпечаток `source_fingerprint` из `web/tools/container_bootstrap.py` | контейнеры compose-проекта `p2pkanban-bootstrap`: `/api/v1/health` и тег образа `<версия>-<сборка>` | версия, затем сборка: коммит или отпечаток этого дерева; коммит с таким же `web/` тоже засчитывается |
| mobile | `versionCode` в `app.json` и `build.gradle` | `adb shell dumpsys package dev.p2pkanban.mobile` на каждом подключённом телефоне | меньше — «отстаёт на N», больше — «впереди исходников» |
| abl | `pkgver-pkgrel` из `abl/packaging/arch/PKGBUILD` | `pacman -Q p2pkanban` | сравнение версий |
| devctl | `DEVCTL_VERSION` и sha256 `devctl/devctl.py` | `devctl --version` и управляемая копия, на которую указывает команда | та же версия с другим файлом — «другая сборка» |

Отставание, опережение и «другая сборка» попадают в блок «Смешанные версии» в
начале сводки и в консоль. Узел и телефон — гейты своих направлений: узел или
APK не из этого дерева значит, что направление на хосте не принято. Установленные
abl и devctl — не гейты: их расхождение видно, но вердикт не меняет.

Контракты из `contracts/compatibility.json` сверяются с тем же развёрнутым:
если направление реализует контракт с версии `since`, а на хосте или телефоне
стоит более старая версия, сводка пишет «контракта там нет» и выносит это в
«Смешанные версии». Так видно, что старый APK не знает, например, кольца
устройств, даже если новый web его уже требует.

Пределы: сборки mobile с одинаковым `versionCode` неразличимы (в APK не
записан коммит). Тег образа web несёт коммит, если узел собран из git, и
отпечаток исходников, если из копии без git.

## Карточки «Ждёт хоста»

Колонка доски «Ждёт хоста» — это и есть список ручной приёмки. Тестер
превращает каждую её карточку в проверку уровня `manual` для направлений из
меток карточки и показывает незакрытые пункты чек-листа. Без
`--interactive` они остаются SKIP. С ним тестер спрашивает «Принято на
хосте? y/n/Enter» и записывает ответ с комментарием в отчёт; следующий патч
двигает карточки по этим ответам.

## Отчёт

Каждый прогон — папка и zip с тем же содержимым рядом:

```text
.uts/
├── uts_20261006T120000Z_r6_749b3d0/     # время UTC, ревизия доски, коммит
│   ├── SUMMARY.md       # читать первым: готовность, вердикты, смесь версий,
│   │                    # почему FAIL (с хвостом лога), карточки, все проверки
│   ├── report.json      # то же для машины, схема p2pkanban-uts-report/1
│   ├── host.json        # ОС и версии инструментов
│   └── logs/
│       ├── web/01-test-devctl-receipt.log
│       ├── …
│       └── abl/01-uts-verify.d/         # отчёт собственного UTS abl
├── uts_20261006T120000Z_r6_749b3d0.zip  # точная копия папки
└── latest.txt                            # имя последнего прогона
```

Лог каждой проверки начинается шапкой (проверка, уровень, гейт, каталог,
команда, время), затем полный вывод, затем итог и код возврата. Тестер
проверяет, что архив совпадает с папкой файл в файл.

Владельцу достаточно прислать zip: в нём сводка, машинный отчёт и все логи.
`.uts/` закрыт `.gitignore`. Снимки devctl его пока не исключают (карточка
«devctl: исключить .uts из снимков workspace»), поэтому обычное место прогона —
копия проекта в `UserTestSpace`.

## Чего тестер не делает

- не запускает, не останавливает и не обновляет web-узел: только читает
  `docker ps` и health; сборочные проверки web используют собственные
  одноразовые compose-проекты web;
- не ставит пакеты, не вызывает `sudo`, `pacman -S`, `systemctl`;
- не трогает телефон, кроме чтения `dumpsys package` и модели;
- не меняет `.devctl` и файлы направлений.

## План и суверенитет направлений

Состав проверок — `tools/ecosystem/uts_plan.json`. Раздел направления в нём —
договор направления с тестером: проверки вызывают только собственные команды
направления из его каталога. Патч направления, который добавляет или
устаревает проверку, правит свой раздел плана; `--self-test` проверяет, что
каждый файл из плана существует. Сверка развёрнутого (`probe`) живёт в
`tools/ecosystem/uts.py`, потому что сравнивает направление с хостом, а не
направление с самим собой.
