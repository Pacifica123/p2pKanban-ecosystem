# Наследие: сжатое ядро устаревших документов

Сюда сводится то, что из старых планов, манифестов и программ стоит помнить,
когда сами документы уже не нужны. Одна запись — одна мысль, которую дорого
открывать заново. Формат намеренно плотный: читается за минуты, а полный
текст восстанавливается из git по указанному пути и коммиту.

## Как читать и пополнять

- Запись: **правило** — почему (одной строкой) — `где живёт сейчас`.
- `⟵ путь@коммит` — откуда взято. Полный текст: `git show <коммит>:<путь>`.
- Пополняется патчем экосистемы, когда направление сжимает свои старые
  документы. Сам исходник удаляет или помечает историческим патч
  направления (суверенитет), а не этот документ.
- Мёртвое не переносится: если мысль уже записана в действующем документе,
  здесь только ссылка на него.
- Отметка `[живо в коде]` — механизм работает и сейчас; документ-исходник
  описывает историю его постройки.

### Диагностика

1. **Красный лог → сначала классификация, потом фикс.** Иначе патч лечит
   последний stacktrace, а не причину. Вопросы: продукт или окружение?
   повторяется? чей слой? какой самый дешёвый probe уменьшит неизвестность?
2. **У повторяющегося сбоя есть стабильное имя семейства** (`REL-ENV`,
   `REL-DB`, `REL-PROC`, `REL-BE`, `REL-FE`, `REL-UIUX`, `REL-DOC`,
   `REL-DEVCTL`, `REL-SEC`, `REL-UNMAPPED`…). `UNMAPPED` — временное
   состояние, не вердикт. Без имени проблему открывают заново под новым
   stacktrace.
3. **Прогон оставляет самодостаточный пакет вскрытия:** логи, отпечаток
   окружения, как разрешились команды, отчёт о вычистке секретов, полнота
   артефактов, следующие команды. Разбор не должен зависеть от прокрутки
   терминала. Наследник в экосистеме — отчёты UTS (`docs/ecosystem/uts.md`)
   и `contracts/error-report/1`.
4. **Пропущенное ≠ пройденное.** Skip из-за отсутствующего инструмента — это
   неизвестность, она опускает оценку, а не повышает. Наследник — честные
   статусы и колонка «Ждёт хоста».
5. **Один зелёный прогон — не стабильность.** Нужны два сравнимых прогона
   того же профиля, start-stop-start и «чистый/грязный» запуск.
6. **Повторяющееся семейство останавливает тактические патчи** и требует
   разбора на уровне процесса.

### Безопасность диагностики

7. **Диагностика создаёт доказательства; патч меняет проект.** Проверка не
   правит отслеживаемые файлы.
8. **Действия с побочным эффектом — только по явному профилю согласия**:
   зависимости, сеть, файлы `.env`, БД, процессы. У каждого — запись и путь
   отката. Dry-run обещает ноль мутаций.
9. **Запись в БД — только в доказанно безопасную цель**: явный тестовый URL
   или своя одноразовая БД. Никогда молча в общую dev-БД.
10. **Чужой процесс не убивается ради зелёного гейта.** Различать свой,
    чужой, зависший PID и занятый неизвестным порт.
11. **Секреты:** инвентаризировать имена, сканировать значения только из
    своих входов; окружающие переменные CI дают ложные срабатывания.

### Оценка готовности

12. **Балл готовности с жёсткими потолками.** Высокий балл не отменяет
    потолок: неизвестный блокер, пропущенный обязательный гейт, нет двух
    прогонов, нет пути через настоящий backend → категория не выше
    указанной. Мокнутый UI не доказывает интеграцию.

### Инструменты

13. **Тяжёлая внешняя зависимость в обязательном пути становится
    инфраструктурным шумом**, похожим на продуктовые ошибки (Playwright:
    бинарники, кэш, загрузки). Обязательный сигнал — лёгкий и свой
    (системный Chromium + CDP, DOM-маркеры вместо координат);
    тяжёлое — необязательно. [живо в коде: `web/tools/uiux/`]

### Как планировать

14. **Единица работы — один проверенный факт**, а не «большая фича»:
    «после патча X истинно Y, проверено Z».
15. **Судьба каждой проблемы одна из пяти:** исправить сейчас, принять как
    ограничение, отложить *с условием возврата*, признать нерелевантной,
    решение владельца. «Когда-нибудь посмотрим» запрещено. (См. E-ADR-002:
    ровно этого не хватило ADR-001.)
16. **Бюджет доказательств соразмерен изменению**: текст → статическая
    проверка, API/БД → интеграция и smoke, развёртывание → чистая машина. Не
    заменять нужный гейт дешёвым нерелевантным.
17. **Новая абстракция — после второго реального использования.**
18. **Крупный осмысленный патч + короткий проверяемый цикл** (найти, проверить
    git, pre-архив, применить, проверки, post-архив, отчёт, коммит только при
    успехе, push после коммита). Этот цикл теперь и есть devctl.
19. **Меньше параллельных манифестов.** Программа стабилизации сама
    закончилась фразой «следующая работа улучшает конкретный слабый сигнал,
    а не добавляет фазу 8» — и это стоит помнить про любые программы.

### Документация

20. **Один факт — один основной документ; выполненный план сжимается до
    решения и результата; документ, повторяющий другой больше чем наполовину,
    сливается, заменяется ссылкой или явно называется историческим.**
    Это правило записано в web ещё при подготовке beta.3
    (`documentation-weight-budget-v1`) и не исполнялось: каталог
    `development/` остался 20 документами. Урок: правило о весе документации
    без проверки не работает — отсюда `tools/ecosystem/docs_audit.py`.
