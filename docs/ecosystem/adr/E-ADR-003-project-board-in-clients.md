# E-ADR-003: доска проекта встроена в клиенты и не синхронизируется

- Статус: **принято** John 2026-10-17 (вариант «только чтение»)
- Дата: 2026-10-17
- Контракт: [`p2p-kanban-project-board/1`](../../../contracts/project-board/1/SPEC.md)
- Заменяет: web seed «P2P Planner roadmap / План работ по проекту»
  (`web/frontend/src/features/bootstrap/lib/projectRoadmapSeed.ts`, описан в
  `web/docs/product/v1-execution-roadmap.md`) — его убирает патч web.

## Задача

John (2026-10-17): доска проекта должна быть встроена в каждый клиент так,
чтобы при подключении узлов она не дублировалась и не несла каскад проблем.
Ориентир — встроенная roadmap-доска web, но там не нужно было думать о
конфликтах.

## Почему нельзя просто повторить seed web

Seed web создаёт обычное пространство и доску **по имени** на каждом узле
отдельно. С одним узлом этого хватало. С несколькими:

- у каждого узла свои UUID и свой ключ доски (`roaming/1` выводит ключ из
  мастер-ключа узла), поэтому две доски с одним именем — две разные доски;
- `web-node-link/1` переносит пространства владельца, и после переноса
  встреча seed и перенесённой копии решается только сравнением имён;
- телефон, подключённый к двум узлам, видит обе;
- правка такой доски на телефоне — это расхождение с репозиторием, которое
  потом надо возвращать руками.

Любой вариант, где доска проекта живёт среди данных пользователя, требует
правил слияния двух её копий.

## Решение

1. **Доска проекта не является данными пользователя.** Она не попадает в базу
   узла, профиль abl и реплику mobile, не публикуется в relay и не
   переносится между узлами. Синхронизировать нечего — дублироваться нечему.
2. **Источник истины не меняется:** `board/board.json` в репозитории, правки
   идут патчами. В клиентах доска только для чтения (выбор John 2026-10-17).
3. **Слияние — выбор старшей ревизии.** У каждого клиента несколько
   кандидатов: копия из своей сборки, кеш, подключённый узел, а у web-узла —
   ещё `main` репозитория на GitHub. `boardRevision` растёт на 1 с каждым
   патчем одного репозитория, поэтому старшая ревизия содержит все прежние.
   Равные ревизии с разными байтами (разошлись ветки) выбираются
   детерминированно и показываются предупреждением.
4. **Постоянный id** (`01a10d38-f902-…`) нужен только чтобы узнать файл.
   Пользовательская копия (импорт «Создать копию») получает новые id и
   остаётся обычной доской человека.
5. **Свежесть без пересборки.** Web-узел раз в час смотрит `board/board.json`
   в ветке `main` того же репозитория, откуда обновляется сам. Телефон и abl
   берут доску у узла и кешируют её, поэтому в мобильной сети без доступа к
   узлу видят последнюю загруженную, с пометкой «из кеша».

## Отвергнутое

| Вариант | Почему нет |
|---|---|
| Редактируемая синхронизируемая доска с фиксированными id | правки расходятся с репозиторием; нужен перенос ключа доски между независимыми узлами и правило, кто владелец; John выбрал «только чтение» |
| Seed по имени, как в web | размножается при подключении узлов, см. выше |
| Копия в сборке без узла | телефон показывал бы доску своей сборки, то есть недели старую |
| Узел — единственный источник | на мобильной сети без узла доски бы не было |

## Последствия

- Новый контракт `p2p-kanban-project-board/1`; порядок: web-узлы → mobile →
  abl. Старый клиент маршрутов не знает и ничего не теряет.
- В каждом направлении появляется копия файла доски (`projectBoard` в
  `ecosystem.json`), её обновляет `tools/ecosystem/project_board.py vendor`.
  Патч направления по умолчанию обновляет свою копию.
- Карточка «Импорт доски в Android» больше не нужна для того, чтобы видеть
  доску проекта на телефоне; импорт пользовательских досок остаётся её темой.
- Версия сборки получает естественную подпись «доска ревизии N, патч X»; её
  может использовать показ версии в клиентах.
