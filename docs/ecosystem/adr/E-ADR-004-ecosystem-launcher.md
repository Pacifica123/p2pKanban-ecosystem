## Задача

John (2026-10-20): метабутстрапер становится лаунчером экосистемы. Базовые
функции:

1. показывать доступные приложения (web, abl; для Android — ссылка на APK из
   сборки expo.dev) с кратким описанием и инструкцией развёртки;
2. устанавливать и запускать — выполнять инструкции развёртки автоматически с
   учётом платформы: на Windows прямо писать, что web нужен Docker, а abl
   показывать серым и некликабельным;
3. обновлять: web и abl автоматически; для Android меняется ссылка на APK, а
   если в `mobile/` уже есть коммит, а нового APK нет — «ожидайте APK»;
4. управлять установленным: то, что сейчас флаги CLI (например, web на
   отдельном порту для теста), — в GUI;
5. показывать состояние: глобальное (что обновилось, изменилось, устарело) и
   локальное (что установлено и как), и сверку между ними;
6. настраиваемый дизайн, как темы приложений; каркас — flat, «пастельный
   пластик», гладкий, с продуманным размером окна.

Сам John склоняется к тому, что лаунчер — отдельный продукт, по категории
между devctl и остальной экосистемой.

## Решение

### 1. Где живёт: новое направление монорепозитория

`launcher/` — пятое направление со своим README, docs, проверками и версией,
на тех же правах, что web, mobile, abl и devctl. Метка на доске — `launcher`,
`patchId` — `YYYY-MM-DD-launcher-…`.

| Вариант | Почему нет |
|---|---|
| Установщик в корне (как в карточке) | у лаунчера свой GUI, своё состояние на машине и свой ритм выпусков; корень по [boundaries.md](../boundaries.md) владеет только связями, а его инструменты — проверки, не продукт |
| Отдельный репозиторий | глобальное состояние лаунчера — это `main` монорепозитория; в отдельном репозитории его коммиты не видны на доске и нужен второй поток патчей. devctl тоже живёт направлением внутри монорепозитория |

Граница: лаунчер **не владеет** ни одним шагом развёртки. Web по-прежнему
ставится `python bootstrap.py`, abl — своим pacman/AppImage-путём, mobile —
APK. Лаунчер вызывает команды, которые направление само объявило, и читает
только то, что направление само опубликовало. Если направление удалить из
дерева, лаунчер показывает его «недоступно», а не ломается; если удалить
лаунчер, ни одно направление не замечает.

### 2. Технология: ядро на стандартной библиотеке, окно на PySide6

Выбор John (2026-10-20): PySide6 и установка зависимостей одним системным
скриптом `install.sh` / `install.bat`.

- **Ядро** — Python 3.11+, только стандартная библиотека: каталог, пробы,
  сверка, `status --json`. Без Qt и без venv работают CLI, UTS и проверки
  devctl, поэтому принцип «корень и devctl без зависимостей» не нарушается.
- **Окно** — PySide6 (Qt for Python, LGPL; не PyQt с GPL или коммерческой
  лицензией), пакет `PySide6-Essentials` с зафиксированной версией. Оно только
  рисует то же состояние, что отдаёт ядро.
- **Установка** — `launcher/install.sh` (Linux, macOS) и `launcher/install.bat`
  (Windows) создают venv в каталоге данных лаунчера на машине пользователя (не
  в checkout и не в системном Python: на Arch `pip install` в систему
  запрещён, PEP 668) и ставят туда PySide6. Повторный запуск безопасен. Одна
  загрузка около 70 МБ, дальше без сети.
- `python launcher/launcher.py` сам находит этот venv. Если Qt нет, лаунчер
  говорит, какой скрипт запустить, и показывает состояние в терминале.
- Оформление — QSS, который генерируется из словаря тем; тени — эффекты Qt.

| Вариант | Почему нет |
|---|---|
| локальная страница в окне Edge/Chrome `--app` | первый вариант L1; это всё же браузер, а John хочет настоящее окно |
| tkinter | на Arch нужен отдельный пакет `tk`; «пастельный пластик» и темы на нём даются тяжело |
| Tauri или Electron | нужна сборочная цепочка и бинарь под каждую платформу |
| PyQt | тот же Qt, но GPL или коммерческая лицензия |

Две оболочки параллельно не держатся: окно Qt — единственное, CLI — запасной
путь.

### 3. Каталог: что лаунчер знает о направлении

Ступень 1 (только чтение) берёт каталог из [`ecosystem.json`](../../../ecosystem.json):
`summary`, `platforms`, `requires`, `install`, `entry`, `docs`. Это карта
корня, а не пересказ устройства направления: в ней только то, что видит
пользователь до установки.

Выполнение действий (ступень 2 и дальше) идёт через контракт
[`p2p-kanban-launcher-entry/1`](../../../contracts/launcher-entry/1/SPEC.md)
(описан 2026-10-20): направление само кладёт в свой каталог
`launcher.json` — какие команды ставят, запускают, останавливают,
обновляют и проверяют его, какие настройки у них есть (для web: порт,
`--listen local|lan`) и как прочитать установленную версию. Лаунчер
выполняет только объявленные команды и только в каталоге направления.
Направление без `launcher.json` остаётся в каталоге «только инструкция».
Команды — только Python-скрипты самого направления, запускаемые интерпретатором
лаунчера без оболочки (`argv[0]` = `{python}`): так лаунчер не знает о Docker,
pacman и makepkg, а значения настроек не могут стать командой.

Порядок появления: контракт в `contracts/` (корень) → web → abl → mobile
(у mobile нет команд: ссылку на APK лаунчер берёт у EAS, п.6).

### 4. Платформа

Лаунчер определяет платформу (`windows`, `linux` и для Arch-based — ещё
`arch-linux`, `macos`) и сверяет её с `platforms` направления.

| Случай | Как выглядит |
|---|---|
| платформа подходит, предпосылки есть | активная карточка |
| платформа подходит, не хватает предпосылки | активная, с жёлтой строкой «нужен Docker Desktop (Linux containers)» и ссылкой |
| платформа не подходит (abl на Windows и macOS) | серая, некликабельная, с причиной «только для Arch-based Linux» |
| Android | на компьютере всегда «скачать APK», без установки |

### 5. Глобальное и локальное состояние

**Глобальное** — `main` репозитория `ecosystem.json#repository` на GitHub:
для каждого направления последний коммит, который менял его каталог (так же
считает обновления updater web), ревизия доски `origin.boardRevision` и
`lastPatchId`; для mobile — ещё последняя сборка EAS (п.6). Ответ кешируется в каталоге пользователя;
без сети показывается кеш с пометкой «из кеша, проверено <время>», как доска
в E-ADR-003. Без токена GitHub разрешает 60 запросов в час — лаунчер делает
один запрос на направление не чаще раза в 10 минут; токен (`GITHUB_TOKEN`)
необязателен.

**Локальное** — три источника, по убыванию доверия:

1. ответ команды `status` направления из его `launcher.json` (ступень 2+);
2. реестр лаунчера `installs.json` в каталоге настроек пользователя
   (`%APPDATA%\p2pkanban\launcher` на Windows, `$XDG_CONFIG_HOME/p2pkanban/launcher`
   на Linux): что лаунчер ставил, из какого коммита, куда, с какими
   настройками;
3. checkout, из которого запущен лаунчер: последний локальный коммит,
   менявший каталог направления, и незакоммиченные изменения в нём.

**Сверка** даёт каждому направлению один вердикт:

| Вердикт | Когда |
|---|---|
| актуально | установленный коммит = последнему коммиту `main`, менявшему каталог |
| устарело | установлен более старый коммит; показывается, сколько коммитов и что в них |
| изменено локально | в checkout есть незакоммиченные правки каталога |
| ожидайте APK | (mobile) в `mobile/` есть коммит новее последней завершённой сборки EAS |
| не установлено | ни реестр, ни `status` не знают установки |
| не работает | `status` направления отвечает ошибкой |
| неизвестно | нет сети и кеша, или у направления ещё нет `launcher.json` |

«Актуально» не значит «принято»: принятие по-прежнему даёт UTS на хосте
(`tools/ecosystem/uts.py`), и лаунчер так это и подписывает.

### 6. Ссылка на APK: лента, которую пишет GitHub Action

Выбор John (2026-10-20): ссылку берём прямо у EAS (expo.dev) по токену Expo,
без файла-указателя через патч. Уточнение John в тот же день: токен один, он
лежит в секретах репозитория GitHub, а лаунчеры его не получают.

- Токен — personal access token со страницы настроек аккаунта expo.dev —
  хранится как секрет репозитория `EXPO_TOKEN` (Settings → Secrets and
  variables → Actions). В репозиторий, патчи, ленту и на машины пользователей
  он не попадает. Токен Expo не ограничивается правами «только чтение»,
  поэтому публиковать его нельзя: с ним можно запускать и удалять сборки,
  менять секреты и настройки проекта.
- GitHub Action `.github/workflows/launcher-apk-feed.yml` (владелец — launcher)
  запускается после push в `main`, менявшего `mobile/`, по расписанию раз в 20
  минут (ловит сборки, запущенные `eas build` руками) и вручную. Он спрашивает
  GraphQL API EAS (`api.expo.dev`) о сборках проекта `ecosystem.json` →
  `mobile.eas` (`owner`, `slug`, `projectId`, `profile`) и публикует
  `apk.json` (`p2p-kanban-launcher-apk-feed/1`) в отдельную ветку
  `launcher-feed` одним коммитом без истории. В `main` бот не пишет.
- В ленте: последняя **завершённая** Android-сборка профиля `preview` (ссылка на
  APK, версия, versionCode, коммит, время, срок хранения артефакта), сборка,
  которая идёт сейчас, и последний коммит `main`, менявший `mobile/`, с
  признаком «входит ли он в историю коммита сборки» — Action считает это по
  полной истории репозитория.
- Лаунчер читает `https://raw.githubusercontent.com/<repository>/launcher-feed/apk.json`
  без токена. «Ожидайте APK» — коммит `mobile/` в `main` не входит в сборку и
  ничего не собирается; «собирается» — сборка идёт; если лента ещё не видела
  последний коммит `main` по `mobile/`, лаунчер так и пишет.
- Запасной путь: если на машине задан `EXPO_TOKEN`, лаунчер может собрать ту же
  ленту сам тем же кодом (`launcher/feed/apk_feed.py`). Без ленты и токена
  карточка Android даёт ссылку на страницу сборок проекта на expo.dev и честно
  пишет, что свежесть сборки неизвестна.
- Если репозиторий переедет, переезжает и секрет: лента привязана к
  `ecosystem.json#repository`, а не к машине (замечание John).

| Вариант | Почему нет |
|---|---|
| указатель `mobile/release/apk.json` через патч | каждая сборка требует ещё одного патча; ссылка приходит позже, чем сборка готова (замечание John) |
| ссылка руками в README | забывается — ровно то, от чего John хочет защиты |
| токен Expo на каждой машине с лаунчером | токен даёт полный доступ к проекту EAS; одна копия в секретах GitHub безопаснее многих |
| публичный токен | см. выше: это права на сборки и секреты проекта, а не только чтение |
| бот пишет в `main` | коммиты бота мешали бы доске и devctl (каждый патч — ревизия доски); отдельная ветка их не касается |

### 7. Внешний вид

Каркас — flat, «пастельный пластик»: крупные скругления, мягкие тени,
спокойная плотность; окно по умолчанию 1120×720, адаптируется до 760 по
ширине. Цвета — четыре темы словаря `p2p-kanban-ui-themes/1`; лаунчер
держит свою копию значений, как остальные направления. Отдельная пастельная
тема, если John её захочет, добавляется в словарь для всех, а не только в
лаунчер (карточка в «Идеях»).

### 8. Самообновление и скачивание

Лаунчер обновляет свой checkout тем же путём, что и направления: из `main`
по коммиту, менявшему `launcher/`. Скачивание экосистемы — полный клон или
sparse по выбранным направлениям (открытый пункт карточки); без git —
архив коммита, как у updater web. Это ступень 5.

### 9. Тестовый web на другом порту

Выбор John (2026-10-20): лаунчер предлагает оба варианта, и выбирает пользователь.

| Вариант | Что это | Чьё решение |
|---|---|---|
| тот же узел на другом порту | прежние БД и каталог, меняется только внешний порт (`start --port`) | уже есть в web |
| второй, тестовый узел | своя БД, свои секреты, свой каталог и порт; рабочий узел не трогается | нужна поддержка в web: сегодня один узел на checkout; появляется патчем web до или вместе с L2 |

`web/launcher.json` объявляет, какие из вариантов web уже умеет; лаунчер
показывает неподдержанный вариант серым с причиной. На 2026-10-20 web держит
один узел на checkout (Compose-проект `p2pkanban-bootstrap`, его тома и
секреты), поэтому второй узел объявлен `supported: false` до отдельного патча
web; карточка «Второй, тестовый web-узел» на доске.
