# Области удаления карточки v1

- Реализация: `v1.0.0-beta.8`
- Протокол: `p2p-kanban-roaming/1`

## Вердикт по исходному поведению

Сохранённая на ПК2 копия была полезным аварийным свойством, но в текущем виде
это протокольный баг: интерфейс называл действие удалением, а между репликами не
передавался факт удаления. Backend публиковал очередной `card.put`, поэтому ПК2
не мог отличить удаление от отсутствия нового события.

Полезную возможность вернуть карточку сохраняет отдельная локальная операция.
Глобальное удаление, напротив, обязано быть наблюдаемым всеми актуальными
репликами и не допускает неявного воскрешения старым снимком.

## Два действия

| Действие | Где действует | Синхронизация | Возврат |
|---|---|---|---|
| Скрыть здесь | Текущий web-узел или Android-устройство | Не создаёт activity, audit, outbox или Nostr event | Через список «Скрытые здесь» |
| Удалить везде | Все реплики с capability доски | Зашифрованный `card.delete` и durable tombstone | Только будущей явной restore-операцией; в v1 её нет |

Старый `DELETE /cards/{cardId}` сохраняет глобальный смысл для обратной
совместимости. Новый интерфейс отправляет `scope=all_devices` явно. Локальное
скрытие использует отдельный endpoint и не притворяется удалением данных.

## Локальное скрытие

Web хранит suppression в `local_card_hides`, привязанной к `local_node_identity`
и пользователю. Эта таблица не входит в web-node link snapshot. Android хранит
аналогичный список в session-bound AsyncStorage конкретного устройства.

Физически стирать единственную локальную запись нельзя: без suppression ID
карточка снова загрузилась бы при следующем pull, а реплика потеряла бы данные,
нужные для корректного merge. Поэтому локальная операция называется скрытием и
остаётся обратимой.

## Глобальный tombstone

При глобальном удалении backend в одной транзакции:

1. выставляет `cards.deleted_at`;
2. создаёт или обновляет `tombstones(entity_type='card', entity_id=...)`;
3. пишет audit и понятную activity;
4. триггером ставит lifecycle-событие в durable roaming outbox.

Publisher шифрует `card.delete` тем же board key, что и `card.put`. Relay видит
только обычную непрозрачную Nostr-запись. Получатель сначала сохраняет
tombstone, затем soft-delete проекции и только после этого отмечает событие
применённым.

## Правило конфликтов

Для lifecycle действует правило `delete wins`, а не обычный LWW:

- `card.put` после известного tombstone отклоняется как `tombstone_wins`;
- карточка из `board.snapshot` фильтруется по локальным tombstone;
- node-link переносит tombstone вместе с capability доски;
- миграция `0014` создаёт tombstone для старых `deleted_at` и ставит их в
  outbox, поэтому исправляются также удаления, сделанные до beta.8.

Такое правило может отбросить позднее offline-редактирование удалённой
карточки. Это сознательный выбор безопасности данных: проигравшее изменение не
должно молча воскресить сущность. Отдельный интерфейс восстановления с
конфликтным черновиком можно добавить позже как новую доменную операцию.

## Совместимость

Все участвующие web-узлы следует обновить до beta.8, Android — до
`1.5.0-mobile.6`. Старый клиент не знает операцию `card.delete` и поэтому не
может обещать глобальную семантику. После обновления и reconnect он прочитает
зашифрованный журнал, применит tombstone и удалит старую проекцию.
