# Принципы планирования и разработки v2

## Решение

Единица работы — не «большая фича», а один проверенный факт о продукте,
релизе или архитектуре.

Пример:

```text
После патча пользователь может распаковать release ZIP, выполнить одну команду
и получить работающий stack без ручного .env.
```

## Почему

Проект уже накопил много планов. Без синхронизации с кодом старые blockers
продолжают управлять разработкой, хотя часть давно закрыта. Поэтому каждый
патч должен либо доказать новый факт, либо обновить источник истины.

## Карточка работы

Каждая задача фиксирует:

- пользовательский или релизный результат;
- затронутые файлы;
- явные не-цели;
- самый дешёвый достаточный gate;
- rollback;
- что станет истинным после применения.

## Направления

| Направление | Примеры |
|---|---|
| Product | CRUD, import, account UX |
| Runtime | bootstrap, sync, offline |
| Safety | auth, backup, destructive guards |
| Evidence | tests, UIX, artifact smoke |
| Truth | docs, OpenAPI, version, roadmap |

Одновременно активным должен быть один узкий slice. Остальное находится в
очереди, а не притворяется параллельным текущим планом.

## Бюджет доказательств

- изменение текста → docs/static check;
- чистая функция → unit;
- API/DB → integration + smoke;
- UI → frontend tests + UIX;
- deployment → clean-machine/artefact smoke;
- release → полный профиль и повторяемость.

Не нужно запускать самый дорогой набор на каждую опечатку, но нельзя заменять
нужный gate более дешёвым нерелевантным.

## Инженерные правила

1. Один источник истины на факт.
2. Код и документация меняются в одном патче, если контракт изменился.
3. Generated files не становятся source.
4. Optional dependency не ломает основной путь.
5. Ошибка среды и ошибка продукта классифицируются отдельно.
6. Destructive действие требует явного target и согласия.
7. Неизвестность записывается как неизвестность, а не как успех.
8. Fallback должен быть проверяемым.
9. Новый abstraction появляется только после второго реального использования.
10. Старый план сжимается после выполнения.

## Судьба проблем

Каждая проблема получает одно состояние:

- исправить сейчас;
- принять как известное ограничение;
- отложить с условием возврата;
- признать нерелевантной;
- требует решения владельца.

«Когда-нибудь посмотрим» без условия возврата запрещено.

## Источники истины

```text
VERSION / код
  → product roadmap
  → ADR
  → архитектурный контракт
  → release evidence
  → исторические планы
```

## Stop/go

Продолжать можно, когда текущий факт доказан и документы согласованы.
Остановиться нужно, когда:

- нужен новый выбор пользователя;
- проверка требует неизвестных credentials;
- destructive target неоднозначен;
- gate показывает data-loss/security риск;
- следующий шаг расширяет scope без разрешения.

## Коротко

Меньше параллельных манифестов, меньше владельцев без задач, один узкий патч,
одно проверяемое утверждение и честный список того, что всё ещё не доказано.
