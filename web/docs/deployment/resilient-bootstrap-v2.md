# Устойчивый bootstrap: сеть, обновление и офлайн-перенос

## Что показали логи

На исходном ПК Rust backend v2.0.0 собрался успешно. Web остановлен нашим wrapper: команда npm завершилась с кодом 124 примерно через 612 секунд. В конце лога есть успешные HTTP 200 скачивания пакетов. Жёсткий лимит десять минут прервал установку; это не ошибка Rust и не доказательство недоступности всех npm-пакетов.

На Windows Docker не загрузил postgres:16-alpine из-за `tls: server did not echo the legacy session ID`. Это ошибка проверки TLS handshake. Причина по одному сообщению не установлена: возможны сетевое вмешательство, proxy, антивирусная HTTPS-проверка или проблема пути/сервиса. Нельзя уверенно утверждать блокировку домена. DNS при ping разрешил адрес; ICMP без ответа ничего не доказывает о HTTPS.

Подтверждённого сообщения о конфликте порта в приложенном логе ПК нет: запуск дошёл до сборки. Код проверки владения портом усилен и покрыт регрессиями, но конкретного конфликтующего процесса по этому логу определить нельзя.

## Обычный запуск после патча

Применить devctl-патч к web-архиву c36ad4c. Выполнить из корня проекта:

```sh
python bootstrap.py start
```

Установщик сначала проверяет runtime-образы в локальном Docker cache. Отсутствующие alpine/postgres скачиваются с тремя ограниченными попытками только при временных сетевых ошибках. Затем отдельно собираются application images. Повтор сборки использует Docker/BuildKit cache. Ошибки зависимостей, целостности, прав доступа и нехватки места не маскируются бесконечными повторами.

npm получает общий проверяемый кеш между сборками через BuildKit cache mount. При сетевом сбое скачанные пакеты повторно используются с тем же lockfile. Для отдельной ошибки `Exit handler never called` пробуется свежий кеш. Не используются удаление lockfile, игнорирование integrity или отключение install scripts. Видимая загрузка продолжается до 30 минут за попытку; отсутствие вывода пять минут считается зависанием. Предусмотрена одна повторная попытка. При завершении по таймеру останавливается группа процессов npm, включая дочерние сборщики.

До окончания подготовки работающие контейнеры не заменяются. Затем создаётся pg_dump старой базы и запускается Compose с готовыми образами: `--no-build --pull never`. Если старый PostgreSQL остановлен, для backup запускается именно его существующий контейнер. Ошибка backup отменяет замену. Данные и секреты остаются в прежних именованных volumes; reset/down --volumes не вызываются. Это не обещание автоматического отката схемы после неудачной миграции: сохраняется backup для восстановления, существующий update/rollback остаётся доступен.

Bootstrap повторно использует порт только подтверждённого stack: Compose project, repository images и mount destinations data/secrets должны совпасть. Остановленный контейнер может сохранить прежний свободный порт, но не считается владельцем чужого занятого сокета. Чужой процесс не завершается. Ручной запуск вне Docker или другой Compose project не усыновляется по одному HTTP-ответу: это требует отдельной миграции.

При запуске новой копии проекта, перенаправленной registry bootstrap в постоянный runtime root, используется код новой копии, помещённый в проверяемый releases-каталог. Старый runtime root продолжает хранить state/backup, а не подменяет новые исходники старой активной версией. Если патч применён прямо в runtime root, где уже выбрана отдельная active release, используйте `python bootstrap.py start --source-dir .` для явного запуска изменённого кода.

## Установка без Docker Hub, npm и Cargo

Надёжный запасной путь — перенос готовых runtime-образов. Нужна одна машина, на которой удалось собрать именно этот patched source. Docker использует штатные [save](https://docs.docker.com/reference/cli/docker/image/save/) и [load](https://docs.docker.com/reference/cli/docker/image/load/).

На доступной машине, из того же проекта:

```sh
python bootstrap.py bundle-export --output p2pkanban-runtime.zip
```

Команда подготавливает пять runtime-образов и сохраняет manifest с SHA-256 tar, image IDs, архитектурой и отпечатком исходников. База, пользовательские файлы и secrets volumes в архив не входят. Набор может занимать сотни мегабайт. Создание не заменяет работающие контейнеры и не перезаписывает существующий ZIP.

Перенести **тот же patched каталог исходников** и runtime ZIP на новую машину. Не менять line endings в пути переноса: отпечаток проверяет байты исходников. На получателе уже должны работать Docker Engine/Compose или Docker Desktop в режиме Linux containers. Затем:

```sh
python bootstrap.py bundle-import p2pkanban-runtime.zip
python bootstrap.py start --offline
```

Импорт проверяет набор файлов, отпечаток исходников, архитектуру Docker server, checksum и загруженные image IDs. Запуск проверяет, что образы после импорта не заменены, и запрещает как pull, так и build. На чистой машине создаются собственные случайные секреты и пустая БД; это установка приложения, не копирование личности владельца. Для данных применяется существующий pairing или отдельный backup/restore.

Windows x64 с Linux containers и Linux x64 используют linux/amd64. Для ARM64 нужен отдельно собранный набор. Checksum обнаруживает повреждение, но не заменяет доверие отправителю: импортировать только свой или полученный от доверенного человека ZIP. Набор содержит исполняемый код.

## Если TLS продолжает ломаться

Проверять нужно Docker daemon, а не только браузер или ping:

```sh
docker version
docker context show
docker pull alpine:3.20
python bootstrap.py doctor
```

Можно сравнить `docker pull` через другую сеть, доступную именно Docker (например, мобильную точку доступа). Если меняется результат, это сужает область поиска, но не устанавливает виновника. Proxy для Docker Desktop/daemon настраивается отдельно от proxy браузера. Не публиковать proxy-пароли или токены из диагностики.

Автоматически переключать TLS в небезопасный режим, править firewall, убивать неизвестные процессы или брать исполняемые образы со случайных зеркал bootstrap не будет. Для управляемого зеркала используются штатные настройки Docker daemon. Никакая программа не создаст недоступные зависимости из ничего: если все сети недоступны, нужен заранее подготовленный набор или доверенный канал его передачи.

Источник трактовки TLS-ошибки: [проверка ServerHello в Go](https://go.dev/src/crypto/tls/handshake_client_tls13.go).

## Android и границы проверки

В приложенном Android-архиве Docker не участвует в APK pipeline. Проверки core contract и переносимого launcher пройдены; менять Android ради этого web-сбоя не требуется. npm/Gradle/SDK там имеют собственные сетевые зависимости. Установка готового APK не требует Docker Hub, но APK assembleRelease на Android SDK в среде подготовки не запускался.

Проверки этого патча используют процессы-заглушки для npm и Docker adapter для сценариев bundle/замены: они проверяют порядок, отказ без изменения stack, кеш, integrity и запреты на сеть. Реального Docker daemon в среде подготовки нет. Полное развёртывание, pg_dump и межмашинный перенос нужно подтвердить на целевых Docker установках; эти испытания не объявлены пройденными.
