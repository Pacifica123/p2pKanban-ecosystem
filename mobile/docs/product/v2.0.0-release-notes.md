# p2pKanban v2.0.0

Новая сессия развития: подключение самостоятельных устройств, Markdown и интеграции. Обновляются web/backend и Android; Windows и Linux используют прежний переносимый bootstrap. Исторические миграции не переписываются, добавляется миграция 0019.

## Подключение без исходного PC-node

Первый сценарий — новое устройство **того же владельца**, с сохранением UUID пользователя, пространств, досок и карточек. Это не приглашение другого человека: member/guest не вправе выдавать личность владельца. Передаются только принадлежащие владельцу пространства; совместные пространства другого владельца исключаются.

1. Пока любой обслуживающий этот аккаунт узел доступен, обновить Android и открыть «Настройки → Подключение устройства → Подготовить». Сохранить актуальные доски в клиенте. Подготовку обновлять после изменений структуры или прав.
2. На новом ноутбуке запустить собственный web/backend обычным `python bootstrap.py start`. Нужна пустая база, без регистрации нового аккаунта. Nostr roaming должен быть включён и иметь настроенные relay.
3. На странице входа открыть подключение v2, создать запрос со сроком 10 минут, передать JSON телефону. Сверить полный отпечаток запроса на обоих устройствах.
4. На Android вставить запрос и явно разрешить подключение. Телефон расширяет подписанную цепочку доверия и передаёт зашифрованный JSON через стандартное меню Android «Поделиться».
5. На ноутбуке открыть ответ, сверить полный публичный ключ отправителя с телефоном, подтвердить и задать новый локальный пароль. Приём снимка и погашение запроса происходят в одной транзакции.
6. Телефон можно выключить. Ноутбук хранит собственные данные и ключ узла, сам читает/публикует события через существующие relay. На странице пространств он также может разрешить ещё одно устройство.

Если PC уже недоступен, а Android не проходил подготовку v2, старого клиентского кеша недостаточно: доказательство полномочий невозможно безопасно восстановить из факта прошлого входа.

## Модель доверия

Используются существующие Nostr device identity, переносимый node-link снимок, ключи отдельных досок и access epoch. Публичная цепочка разрешений связывает пользователя, пространство, доску, epoch, ключ устройства, право делегирования и expiry. Каждый следующий подписант должен быть адресатом предыдущего разрешения. Срок и область прав расширять нельзя. Корень проверяется относительно уже доверенного владельца доски; нового централизованного сервера нет.

Подписи Schnorr связывают полный упорядоченный набор зашифрованных фрагментов. Снимок зашифрован NIP-44 v2 для ключа получателя; пароль, хеш пароля и master secret исходного узла не передаются. Внутри шифротекста присутствуют переносимые ключи досок: это необходимые права самостоятельного участника. Проверка отпечатков защищает первоначальный обмен от подмены; сравнивать нужно полностью, по независимому визуальному каналу.

Запрос действует 10 минут и принимается один раз именно создавшим его пустым узлом. Повтор/чужой ключ/изменённая подпись отклоняются. Подготовленные полномочия действуют до 90 дней, цепочка ограничена восемью разрешениями. Делегирование не продлевает исходный срок. До истечения нужно обновить подготовку от доступного владельца с действующими полномочиями; после истечения цепочки может понадобиться исходный корневой узел. Мгновенного глобального отзыва на отключённых узлах нет. Ротацию прав/epoch следует проводить осознанно: она ещё не является распределённым протоколом членства.

Максимальный открытый снимок — 8 MiB, HTTP-конверт — 16 MiB. Нужны согласованные часы. UI использует JSON-файлы/копирование, не QR и не телефонный HTTP-сервер. Файлы ответа можно повторно передать до expiry, но импортировать повторно нельзя. Секрет телефона хранится в SecureStore; подготовка на диске зашифрована этим ключом. Локальные очереди клиента сохраняют прежнюю модель хранения.

## Markdown и работа с карточками

Описание остаётся обычной строкой Markdown. Поддержаны заголовки, bold/italic/strike, списки, ссылки, цитаты и код. Редактор — исходный текст, панель вставки и просмотр. Старый текст отображается как текст; похожие на Markdown конструкции интерпретируются как Markdown. Произвольный HTML и загрузка изображений отключены, ссылки ограничены HTTP(S)/mailto.

Web: комментарии используют настройку отправки checklist item (Enter, Ctrl+Enter или кнопка), с учётом IME. Checkbox наследуют тему/accent; приоритет отображается четырьмя звёздами. Android: кнопки вверх/вниз меняют позицию карточки внутри колонки через существующую локальную очередь; перенос между колонками сохранён. При исчерпании числового промежутка операция сообщает об этом, не назначая совпадающую позицию.

В обоих клиентах сортировка по priority включается отдельно для колонки, от urgent к low. При равном приоритете используется ручная позиция. Это только представление: позиции не перезаписываются; при выключении прежний ручной порядок возвращается. Во время сортировки перестановка отключена. Выбор сортировки локален экрану и не синхронизируется.

Android: текущую карточку можно передать как `.md` через системное меню или открыть создание заметки через Obsidian URI с подтверждением. Длинный текст передаётся файлом. Наличие Obsidian в меню зависит от установленных приложений; автоматического выбора vault и двусторонней синхронизации нет.

## devctl

В web-доске есть привязка проекта к локальному workspace, экспорт project.json и явный preview/import receipt. Конвертер `tools/devctl_receipt.py` читает уже записанные результаты devctl 0.7. Браузер не запускает shell, приложение не выполняет команды из receipt. Результат сохраняется как evidence; автоматически завершать карточки/пункты нельзя. Повтор одного receipt идемпотентен, изменение содержимого с тем же ID отклоняется. Подробнее: [интеграция devctl](../integrations/devctl-v2.md).

## Границы автономной синхронизации

| Данные | Состояние v2 |
| --- | --- |
| Карточки, описание Markdown, priority, позиции, удаления | Существующий зашифрованный roaming и merge |
| Чек-листы и оформление доски | Существующие roaming-механизмы |
| Пространства, доски, колонки | Снимок при pairing; последующие структурные изменения не имеют полной автономной репликации |
| Комментарии, метки, участники/приглашения | Снимок/HTTP; не обещана полная синхронизация между автономными узлами |
| devctl-привязки и receipts | Только локальная база узла; не входят в pairing-снимок и roaming |
| Пароли/сессии/настройки транспорта узла | Локальны узлу; новый пароль задаётся отдельно |

Android добавляет в подготовленный снимок доступные локальные карточки и загруженные чек-листы. Отсутствующая в частичном кеше карточка не считается удалённой: нужны явные tombstone/queued delete. Новая неизвестная снимку колонка требует повторной подготовки. Перенос снимка не превращает ограничения существующего sync в решённую задачу. Для обмена между городами нужны доступные relay; без связи изменения остаются локально до восстановления транспорта.

## Обновление и откат

Применять web-патч к архиву `11d8524`, Android-патч к `7a89518`, через devctl соответствующего workspace. Сначала web/backend, затем Android. Зависимости устанавливаются из обновлённых lockfiles. Обычный запуск: `python bootstrap.py start`; `--no-open` необязателен и только отключает открытие браузера. Android: `npm ci`, `npm run apk`. Версия APK 2.0.0, versionCode 20.

Перед миграцией сохранить обычную резервную копию PostgreSQL. Старый backend не знает миграцию 0019: откат кода без восстановления согласованной БД не поддерживается. Не удалять volumes ради исправления запуска. Проверки Docker, реального Android APK и разных ОС следует выполнить на целевых машинах; исходники и автоматические проверки не заменяют эти испытания.
